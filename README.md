# AuvAdRules

供 **AdGuard Home** 和 **AdGuard 客户端 DNS 防护**使用的同一份域名过滤订阅。
基于 HaGeZi Normal，合并本仓库经复验的自定义域名规则。当前自定义增补为空；
首版提供统一维护、更新和发布，不宣称比 Normal 多覆盖了开屏广告。

推荐订阅地址（两端相同；GitHub Pages）：

```text
https://keman5.github.io/AuvAdRules/filters/dns.txt
```

Raw 备用地址（部分网络可能无法直连）：

```text
https://raw.githubusercontent.com/keman5/AuvAdRules/main/filters/dns.txt
```

两个地址发布相同规则，只订阅其中一个。Pages 发布可能比仓库提交晚数分钟；
Raw 更新不依赖 Pages 部署完成，切换地址前应确认设备能下载。

使用原生 `||domain^` / `@@||domain^` 语法，无仅限 A 查询的限制，适用于 A、AAAA
及其他 DNS 查询类型。IPv6 是否真正经过过滤，还取决于设备的 DNS 路由。
不关闭 IPv6，不替换 DNS 服务器，不包含 URL Rewrite、MITM 或 Safari 元素规则。

## 家里 Wi-Fi：设备不安装客户端

1. Home → 过滤器 → DNS 黑名单 → 添加自定义列表，填入上面的订阅地址，启用并更新。
2. Home 开启 DNS 过滤。路由器 DHCPv4 把 Home 的固定局域网地址下发为 DNS；
   或让所有客户端使用路由器、由路由器仅转发给 Home，避免循环转发。
3. IPv6 RA 的 RDNSS／DHCPv6 DNS 也指向 Home 的稳定 IPv6 地址，或指向只转发给
   Home 的路由器。不能同时下发运营商／未过滤的 DNS 作为“备用”。Android 等设备
   可能使用 RA 而不使用 DHCPv6，因此两条路径都要检查。
4. Home 如提供 IPv6 DNS 服务，需要监听相应 LAN 地址，且允许 LAN 访问 TCP/UDP 53。
   DNS 经 IPv4 到 Home 同样可以过滤 AAAA；不用为此禁止 IPv6 地址解析。
5. 重连 Wi-Fi／续租后验证。已有广告素材、DNS 缓存可能继续使用，不应为测试删除用户数据。

仅更改 DHCP 不能强制所有设备服从：固定 DNS、自带 DoH/DoT、VPN、Private Relay
等可能使用不同路径。路由器可按需约束 LAN 的 TCP/UDP 53（IPv4 与 IPv6 都处理），
但不能由此宣称所有 HTTPS/DoH 或硬编码 IP 都被过滤。不要在不知道家庭网络拓扑时
直接套防火墙命令，也不要封禁所有 443 流量。

## 离家：手机客户端本地过滤

1. 在客户端的 **DNS 防护 → DNS 过滤／DNS 过滤器**添加同一订阅。不要加到 Safari
   内容规则列表或代理订阅列表中。
2. 开启 DNS 防护并确认实际运行。测试版的“代理”开关不等于开启 DNS 过滤。
3. 使用离家可达的可信 DNS 上游，例如客户端内置的加密 DNS；**不要把仅家中可达的
   私网 Home 地址设为离家唯一上游**。客户端本地规则不依赖 Home 在线。
4. 若需要让离家查询也经过自己的 Home，另行提供可达的 DoH/DoT 或私有 VPN。
   这不是加载本地规则的前提。不要公开无访问控制的家庭 DNS 端口。
5. 开启客户端支持的自动过滤器更新；各平台后台调度由操作系统决定，不能保证即时刷新。

家里客户端也开着时，可使用 Home 作上游形成两层过滤；本地已拦截的查询不会到 Home，
所以两边日志不必同时出现同一请求。

## 更新、自定义与回退

GitHub Actions 每 12 小时检查上游，可手动运行；GitHub 可能延迟调度，长期无活动的公开
仓库定时任务也可能被平台停用。新增自定义规则提交后触发更新。失败时不发布，查看 Actions
状态处理；客户端／Home 仍需按各自周期拉取。首次使用应手动更新并核对规则数量。

- 默认规则来自 HaGeZi Normal，已用 `filter_34` 时不必重复启用同源列表。
- 修改 `rules/custom.txt`，只允许完整域名规则与例外。为每条新增封禁记录来源、App 版本、
  新请求命中、A/AAAA 结果，以及登录、搜索、商品详情等功能回归。
- `@@||needed.example.org^` 可作为误杀例外，影响范围包含该域名及子域名，需先核对。
- 生成器拒绝 HTML／未知语法／空列表／异常大小和超出 -30% 至 +50% 的数量变化。
  这能发现部分下载故障，不能代替对误杀的复验。
- `filters/manifest.json` 保存来源和输出校验值。回退时可将订阅 URL 中 `main` 换成已验证
  的旧提交 SHA；固定版本不会继续自动更新，问题修复后切回 `main`。

```sh
bash build.sh test
bash build.sh update
```

发布只通过 `bash build.sh publish`，要求先审阅并提交本仓库变化。不要提交私网配置、
日志、认证信息或私有项目文件。上游来源和 GPL-3.0 授权见 [SOURCES.md](SOURCES.md)。

## 验收边界

DNS 能阻止广告域名解析，不能可靠区分同域名的广告路径与购物／登录接口，也不能删除
缓存广告、拦截硬编码 IP 或自动解密 HTTPS。因此不承诺“所有开屏广告全部消失”。

分别测试：家中 Wi-Fi（客户端关）、蜂窝网络（客户端 DNS 开）、双栈网络；每种场景均需：

- 新查询确实到预期过滤器，已封禁域名的 A 和 AAAA 返回拦截结果，正常域名仍可解析。
- 每款目标 App 冷启动观察广告，同时验证登录／搜索／主要功能；保留广告缓存状态的说明。
- 查询不存在时先排查 DNS 缓存／旁路解析，不猜测封禁主域名；记录命中但广告仍在时检查其他
  请求或缓存。DNS 通过与“App 无广告”是两项独立结论。

目前没有对本次用户手机／家庭网络出具全量通过结论。
已完成的生成器、公开下载和双栈 DNS 引擎检查见 [ACCEPTANCE.md](ACCEPTANCE.md)。
